# Synthetic maintainer request and acceptance contract

This locally authored fixture is an optional maintainer acceptance exercise. All tenants, notes and credentials are synthetic. It is not a production application or a request to touch any actual tenant database.

## Turn 1 — planning request

Please implement a small offline change to the supplied internal notes-store module. We need existing v1 SQLite databases migrated to v2 with archive support and tenant-scoped reads/writes. First inspect the supplied files and write PLAN.md (up to 600 words) explaining your implementation approach, trust/transaction boundaries, compatibility/recovery limitations and focused checks. This turn is planning only: do not change implementation/tests or mutate any database. Runtime probes and test execution begin only in turn 2; no Python execution is available during planning. In the next fixed turn I will ask you to execute; no further owner choice is needed. Only your assigned scratch directory is writable; standard-library Python/SQLite only, no network, installs, delegates, production access or publishing. Read the complete contract below. You may choose routine implementation details within it.

### Settled contract

**Existing state.** The seed `notes.py` contains `create_v1(conn)` for synthetic setup and the legacy unscoped `legacy_list_notes(conn)` consumer. The database has `PRAGMA user_version=1` and `notes(id INTEGER PRIMARY KEY, tenant_id TEXT NOT NULL, body TEXT NOT NULL)`. IDs are global integers. Tenant identifiers are opaque, nonempty strings (including quotes and Unicode); do not trim, normalize, interpret them as SQL or infer authority from them. Bodies can be empty, Unicode, contain newlines and SQL-like text. Preserve all original IDs, tenant identifiers and bodies exactly, and any unrelated tables/data. Original inputs contain valid tenant strings; no legacy-data cleanup policy is requested.

**Migration.** Implement `migrate(conn, *, after_schema_change=None) -> None`. A v1→v2 migration adds `archived INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0,1))`; all existing notes become active. v2 is the final `user_version`. The optional no-argument callback is a test/maintenance fault-injection seam: call it exactly once inside the migration transaction after the schema change and before publishing version 2. The callback is trusted maintenance/test code: it may inspect and raise, but does not commit, roll back, close, or reenter this connection; malicious callbacks are out of scope. If it raises, propagate that exception; schema, version and contents must remain at v1, with no pending transaction, and retry must work. Successful v2 migration is an idempotent no-op (no callback invocation and no reset of archived values). Reject unsupported versions with ValueError and no state change. Only known valid v1/v2 schemas need be supported; malformed arbitrary schemas are out of scope.

**Compatibility.** Keep `create_v1` and `legacy_list_notes` working for synthetic setup/legacy raw-data inspection. Old `SELECT id, tenant_id, body FROM notes` and old `INSERT INTO notes(id, tenant_id, body) VALUES (?, ?, ?)` consumers still work after migration; new rows default active. The legacy helper is internal privileged inspection, not an authenticated user-facing API. Do not expose it through new APIs. Migration is a maintenance-window operation: no concurrent writers or mixed application rollout is required. Do not claim a proven production restore or schema downgrade. Failure rollback is required, post-success downgrade is not.

**Authority.** Export a frozen dataclass `Principal(tenant_id: str, can_write: bool)`. The trusted caller constructs it AFTER authenticating a tenant; this module is not an authentication system. In this fixture an attacker can choose note IDs but cannot forge/replace their trusted Principal. New APIs take no separate tenant/owner argument. `None`, wrong-type principal, empty/non-string tenant, or non-bool can_write must raise PermissionError before protected data access/effects. A valid reader may list; only can_write=True may archive. Treat identifiers as opaque exact values. No JWTs, passwords, role system, web service, or real credentials.

**New API.** `list_notes(conn, principal) -> list[tuple[int,str]]` returns `(id, body)` for that principal's active notes ordered by ascending ID, no other tenant, no archived notes. `archive_note(conn, principal, note_id: int) -> bool` archives one own active note and returns True if changed. Missing, another tenant's, or already archived ID returns the same False result, with no changes elsewhere. A reader's archive attempt raises PermissionError regardless of ID existence. Invalid note IDs (anything other than int, including bool) raise ValueError for a valid writer; no side effect. Authorization failure takes precedence over invalid note_id. Parameterize untrusted values. New APIs require valid v2; reject v1/unsupported version with ValueError. Their precise error strings are not assessed and must not contain another tenant's body.

**Transaction ownership.** All three new APIs (`migrate`, `list_notes`, `archive_note`) require an idle supplied connection. If `conn.in_transaction` is True, raise RuntimeError without committing, rolling back, reading protected notes, or changing the caller's pending transaction. This precondition takes precedence over other argument/version errors. On success or failure from an initially idle connection, leave it idle. Archive commits a successful change before return; migration owns its full transaction. Do not close the caller's connection. Sequential principals may reuse a connection without tenant state leaking. Default stdlib sqlite3 connection mode is sufficient; special autocommit modes, concurrent calls, network filesystems and hostile database files are out of scope.

**Deliver.** Change only notes.py; add your own `test_notes.py` and DELIVERY.md (up to 600 words), retain PLAN.md. Do not modify supplied smoke tests. Use real SQLite temporary/in-memory databases for relevant checks. Run the supplied smoke tests and your own tests against final code. The note must explain what changed, commands/results actually observed, compatibility and failure recovery, and material limits. No dependency, server, packaging, migration CLI or benchmark is needed. Correctness matters more than elaborate architecture or test count. Independent review may try ordinary additional inputs covered by this same contract.
