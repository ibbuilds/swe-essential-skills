# Security change review

Use for a security-sensitive diff or a requested security review. Narrow harmless changes rather than staging a full audit.

1. Establish the compared revisions and intended behavior. Inspect changed functions plus callers, shared middleware, configuration defaults and tests. History can explain why an apparently redundant guard exists; it is evidence to investigate, not proof that the guard is obsolete.
2. Follow changed data to a consequential sink: storage, command execution, network destination, deserialization, privileged operation, template, credential or log. Also inspect removed checks and changed ordering. A safe helper does not help a caller that bypasses it.
3. State an attack hypothesis with actor, controlled input, prerequisite, path and impact. Prefer “a tenant member can export another tenant's invoice by substituting this ID” to “possible access-control issue.” Check whether an earlier authoritative layer actually rules it out.
4. Use a source trace when it establishes the reachable failure. Where consequential uncertainty remains, construct or propose the smallest safe distinguishing check within the requested review mode and existing authority. For an executable authorization-regression check, use two isolated fixture tenants and verify both the response and absence of side effects. For a path issue, include normalization and symlink behavior relevant to the platform; do not read real sensitive files to demonstrate it.
5. Propose a fix at the owner of the invariant, then inspect other callers sharing that failure mode. Avoid a one-route patch when a shared query or policy is the actual defect. Avoid broadly rewriting unrelated authentication code to fix one missing permission.
6. For a single requested review, finish after reporting supported findings and material limitations for the reviewed revision; unresolved findings do not authorize repair or continued monitoring. When correction review is requested or remediation is authorized, recheck the corrected revision and relevant legitimate flows. Record rejected findings with the concrete constraint preventing exploitation; reopen them if that constraint changes. Bound repeated review by the agreed scope and stopping condition, not a commercial tool's score.

**Illustration:** An invoice export moves to a worker. The HTTP route checks membership, but the worker fetches the invoice by ID alone. Determine whether the queued job carries a trustworthy tenant binding and whether authorization is meant to hold at submission or execution. A delayed job after membership revocation may need execution-time authorization; a previously authorized immutable administrative job may have different semantics. Encode the chosen rule and test both timing and cross-tenant substitution.

A useful finding includes location, reachable scenario, impact, evidence, proposed control and a proposed or observed regression check, labeled accordingly. Do not inflate severity from a dangerous API name without showing the reachable conditions.


## Authorization errors are not ordinary policy denials

When changing an authorization adapter, policy loading or required context, distinguish a policy denial from an unavailable check, evaluation error or incomplete input. Inspect how the actual engine combines decisions and diagnostics: default deny does not necessarily make an erroring guard deny access. Enforce the accepted safety/availability contract before the protected effect, including required-policy/context completeness and explicitly allowed fallback. Do not silently grant access or impose blanket denial for unrelated tolerated errors.

For example, a general export permit can remain satisfied while a required suspension guard errors on missing context. A missing guard may produce no evaluation diagnostic at all. Verify the affected failed/missing required guard path and legitimate access under tolerated errors; a clean diagnostics list alone does not prove the intended policy set was supplied. Reuse existing loader/schema guarantees where they establish those preconditions. This is not a requirement to replace the authorization engine or add another cache policy.
