# Planning mechanisms and original adaptations

Primary sources inspected on 22 October 2026. These are practitioner mechanisms,
not controlled evidence that this suite saves tokens. Moving source links may
change; inspect the exact content and license before any future textual reuse.
No third-party skill text is vendored here.

| Source | Useful mechanism | Our adaptation / rejected overhead |
| --- | --- | --- |
| [Matt Pocock: grilling](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md) | Separate investigable facts from user decisions; ask unblocked decisions in dependency-aware rounds with recommendations | Ask a manageable material batch, not every possible question; explicitly bounded uncertainty can remain. Older one-question-at-a-time descriptions do not describe this current source |
| [Matt Pocock: domain modeling](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/domain-modeling/SKILL.md) | Resolve contradictory terms against actual code and preserve the agreed vocabulary | Reuse existing terminology ownership; no required new glossary filename or ADR for ordinary choices |
| [Matt Pocock: wayfinder](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/wayfinder/SKILL.md) | Distinguish decisions, implementation and unresolved scope | Keep usable next commitments without requiring a separate tracker |
| [Matt Pocock: to-spec](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-spec/SKILL.md) and [to-tickets](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-tickets/SKILL.md) | Synthesize existing context and derive verifiable dependency-aware slices | Preserve essential journeys and existing records; do not publish tickets or force exhaustive story lists simply because a skill runs |
| [GitHub Spec Kit: clarify](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md) and [analyze](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md) | Check coverage, ambiguity, contradictions and consistency rather than trusting document polish | Import-first gap review; risk-ranked questions without arbitrary fixed interview caps. A coverage count does not prove a good plan |
| [Shape Up: shaping principles](https://basecamp.com/shapeup/1.1-chapter-02) | Concrete, bounded work with room for implementation judgment | Resolve expensive dependencies before commitment; defer cheap reversible details explicitly rather than mandate exhaustive waterfall design |
| [SVPG: four risks](https://www.svpg.com/four-big-risks/) | Distinguish value, usability, feasibility and viability | Product and engineering readiness are related but not interchangeable; an agent conversation cannot establish customer demand |
| [Teresa Torres: discovering solutions](https://www.producttalk.org/discovering-solutions/) | Connect outcomes, observed opportunities, solutions and assumption tests | Keep evidence and hypotheses separate; recommend proportionate validation without claiming invented interviews or performing unauthorized outreach |
| [April Dunford: positioning](https://www.aprildunford.com/post/a-quickstart-guide-to-positioning) | Examine alternatives, differentiated capabilities, value, relevant customers and market context | Make positioning an evidence-aware product choice, not a generated slogan or mandatory competitive research exercise for an internal tool |

## What changed in this suite

- Project planning accepts existing material or develops a plan from an idea.
- Product discovery and product definition own missing product decisions instead
  of leaving architecture to invent them.
- Requirements, architecture and construction preserve readiness before dependent
  implementation while allowing scoped investigation and well-defined corrections.
- The plan remains one coherent source of decisions, acceptance and uncertainty;
  using another skill is not a reason to repeat questions or create another copy.

## Evidence still needed

Static review can identify duplicate instructions, contradictory boundaries,
missing transitions and portable-reference failures. Only real use can establish
activation reliability, question burden, downstream rework or net usage impact.
Future evaluation should compare adequate outcomes and total effort, not merely
shorter replies, fewer tests or fewer planning tokens. Live evaluation remains
separate and deferred under the owner's usage constraint.
